# Terraform audit report

Date: 2026-11-22
Scope: every file in `terraform/`, repository Terraform ignore rules, CI validation workflow, and the existing Ansible inventory/role context relevant to port 9100. No AWS resources or credentials were accessed or changed.

## Summary and verdict

**READY WITH BLOCKERS** for remote Terraform initialization. The configuration is structurally valid and local validation passes with Terraform 1.17.2 and AWS provider 5.100.0. Normal initialization is blocked until the operator supplies an existing S3 state bucket and backend configuration. The bucket must be prepared outside this Terraform configuration; this project deliberately does not create it.

## Problems and corrections

1. `security.tf`: web Node Exporter ingress previously accepted connections from the entire VPC. It now accepts port 9100 only from the monitoring security group.
2. `security.tf`: monitoring Node Exporter ingress previously accepted connections from the entire VPC. It now allows matching monitoring security-group traffic for local monitoring-server scraping. No monitoring UI or SSH port is exposed to `0.0.0.0/0`.
3. `.terraform.lock.hcl`: no lock file existed before validation. It was generated by local init and should be committed to keep provider selection reproducible. The `.gitignore` does not exclude it.

## Security findings

- SSH on both instances and Prometheus (9090), Grafana (3000), Nagios HTTP (80), and Nagios HTTPS (443) on the monitoring instance are limited to `admin_cidr`. The variable validation rejects invalid IPv4 CIDRs and `0.0.0.0/0`; use a current administrator public IP `/32`.
- Public HTTP port 80 is open only on the web instance as intended.
- Node Exporter port 9100 uses security-group sources, not a public CIDR.
- Both root volumes are encrypted; both instances require IMDSv2 tokens.
- The project registers only a public SSH key; Terraform does not read the private key.
- No credentials or sensitive Terraform outputs are defined. AWS authentication is supplied by the local AWS CLI/provider credential chain.
- `.gitignore` excludes Terraform state, local variable files, credentials, and `.terraform/`; it does not exclude `.terraform.lock.hcl`.
- Egress is unrestricted for both groups to support package installation and outbound service traffic. No narrower egress requirement was provided.

## Backend findings and prerequisites

`backend.tf` intentionally leaves S3 backend values to `-backend-config`. `backend.hcl.example` sets `encrypt = true` and `use_lockfile = true`, requiring Terraform 1.10 or later. Bucket, key, and backend region are supplied once in the backend config; provider region remains an independent AWS provider setting in `terraform.tfvars`/variables because backend initialization occurs before provider evaluation. Keep both region settings consistent. No DynamoDB table is required by this native lockfile configuration.

Before ordinary `terraform init`, an operator must provide an existing S3 bucket in the backend region and a unique state key, with S3 versioning, server-side encryption, Block Public Access, and least-privilege IAM access configured. The identity also needs permissions for state-object access and the `.tflock` object used by native locking. These prerequisites were not created or checked against an AWS account.

## Validation results

Run from WSL Ubuntu in `terraform/`:

- `terraform fmt -recursive`: PASS (formatted `security.tf`).
- `terraform fmt -recursive -check`: PASS.
- `terraform init -backend=false`: PASS; initialized the AWS provider without contacting the remote backend. Downloaded provider `hashicorp/aws v5.100.0` (signed by HashiCorp) and generated `.terraform.lock.hcl`.
- `terraform validate`: PASS after correcting an unsupported inline ingress argument discovered during the first validation attempt.
- `terraform providers`: BLOCKED in this backend-disabled workspace. The command requires the declared S3 backend to be initialized and reports `Backend initialization required`; normal remote initialization needs the bucket prerequisites above. `terraform validate` independently confirms the provider configuration is valid.
- No plan, apply, destroy, or AWS-resource operation was run.

Terraform is not on the Windows PATH, but WSL has Terraform v1.17.2. Provider initialization took longer than usual but completed successfully.

## Remaining manual steps

1. Review and commit `.terraform.lock.hcl` with the configuration.
2. Create or select and secure the remote state bucket separately; do not use the placeholder bucket.
3. Create a private backend config file outside the repository from `backend.hcl.example`; set the actual bucket and a suitable unique key. Keep its `region` aligned with the configured AWS region and preserve `encrypt = true` and `use_lockfile = true`.
4. In WSL, configure the intended AWS CLI/SSO identity, update local `terraform.tfvars` with the administrator CIDR and public-key path, and verify the AWS identity before any plan.
5. Run normal `terraform init` with that backend config, then inspect a plan. No infrastructure is provisioned by this audit.
